# Blueprint configuration

## Concept

An **event** is a blueprint automation triggered when a Reolink **binary sensor changes from `off` to `on`**. It is not a device-wide monolithic automation. Different events can use the same physical camera while selecting different lenses, resolutions, recipients or destinations.

## Inputs

| Input | Required when | Meaning | Default |
| --- | --- | --- | --- |
| `event_id` | Always | Stable ID, letters/digits/`_`/`-`, 1–80 chars | — |
| `detection_sensor` | Always | HA `binary_sensor.*`, trigger `off → on` | — |
| `video_camera_id` | Immich video; otherwise fallback for ntfy video | Key in `cameras.json` | empty |
| `ntfy_video_camera_id` | Optional for ntfy video | Override camera key (different lens, physical camera, etc.) | use `video_camera_id` |
| `snapshot_camera` | Either output uses **image** | HA `camera.*` entity, including a lens-specific snapshot source | empty |
| `video_duration` | Immich video | Seconds, 1–40 | 20 |
| `ntfy_video_duration` | ntfy video | Seconds, 1–40 | 10 |
| `ntfy_mode` | — | `none` / `image` / `video` | `none` |
| `ntfy_video_stream` | ntfy video | `clear` or `fluent` | `fluent` |
| `ntfy_target` | ntfy enabled | HA topic entity such as `notify.front_door` | empty |
| `ntfy_title`, `ntfy_message`, `ntfy_priority` | Optional ntfy | Customize the notification, priority 1–5 | default message / 3 |
| `immich_mode` | — | `none` / `image` / `video` | `none` |
| `immich_video_stream` | Immich video | `clear` or `fluent` | `clear` |
| `immich_config_entry_id` | Immich enabled | The native HA Immich config entry (UI selector) | empty |
| `immich_album_id` | Immich enabled | UUID of an **existing** album, **not its name** | empty |
| `cleanup_files` | — | Delete locally created medium after successful action | `true` |
| `debug` | — | Extra `logbook.log` diagnostic entries | `false` |

### Image versus video

- `ntfy=image` sends a **current** camera image directly with `ntfy.publish`. No video recording, upload or intentional delay is needed first.
- `immich=image` writes one JPG file with `camera.snapshot` and uploads it with `immich.upload_file`.
- `ntfy=video` records an MP4 from the selected RTSP stream, then sends it to ntfy. Delivery can only happen after the video is complete.
- `immich=video` records and uploads the MP4 to the selected existing Immich album.
- The two output modes are independent. For example, **ntfy=image / Immich=video** works with the same trigger and does not make the image wait for the video.
- `none` disables the corresponding destination. Both set to `none` is an invalid configuration.

### Clear and Fluent are not percentages

`clear` uses a high-resolution `main` RTSP stream, `fluent` a smaller `sub` RTSP stream. The recorder copies each selected stream and available audio without transcoding. A quality value such as “80%” is intentionally **not** included.

### Two lenses on one device

Suppose a physical camera exposes wide and tele lenses on two RTSP channels. Define two keys, such as `garden_wide` with channel `1` and `garden_tele` with channel `2`, using the same IP and credentials **only after verifying your model's channel mapping**.

For an event that archives the **tele Fluent** video, select:

- **Video camera ID:** `garden_tele`
- **Immich output:** Video
- **Immich video stream:** Fluent
- **Immich album:** the desired album UUID

The Reolink integration's `camera.garden_fluent_lens_1` is a Home Assistant **camera entity** and is not directly an entry for our RTSP recorder. For direct snapshot or ntfy image, however, you can select an appropriate Home Assistant `camera.*` entity in `snapshot_camera`.

## Parallelism, cleanup and failures

Every blueprint instance has `mode: parallel` with a maximum of 20 automation executions; the shared video script supports up to 12 parallel calls. These are explicit concurrency ceilings, **not** a guarantee of 20 concurrent streams from the camera. The two destination branches have distinct media filenames and share a run ID.

The `cleanup_files` switch applies only to local media generated by this workflow. It will never delete your Immich asset. It runs **after** the native ntfy/Immich action returns successfully. If a recording or destination action fails, the file is retained. Orphaned `.part` files from interrupted recordings are also retained and require manual attention.

There is no retry queue, event-level cooldown, rate limit, pre-event lookback or alarm-system logic. These are deliberate scope boundaries.

## Debugging

Enable `debug` temporarily and inspect Home Assistant **Automation Traces**, **Script Traces** and **Logbook**. Many errors from recording or cleanup also create persistent notifications. Native ntfy/Immich action failures are primarily visible in traces and Home Assistant logs; **persistent notification delivery is not guaranteed for those failures**.
